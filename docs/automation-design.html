1 · The foundation every automation shares

Every button press follows the same path. Understanding it once explains all four automations.

  1. The browser calls the API The user is signed in with Google (only @opptra.com accounts). The API checks their role in Postgres on every request, so removing someone takes effect in seconds, not when their login expires.
  2. The API writes a run row and queues a job A row in the runs table records who asked for what, when. The job goes into a Redis queue and the API answers immediately with a run id the browser polls. why If the server restarts mid-job, the queue survives (Redis persists it) and the run row means nothing is ever lost silently. The browser never waits on a long request that could time out.
  3. The worker picks the job up, one at a time A single worker process executes jobs serially and is the only thing that ever talks to Unicommerce, Google, or Neon. why Unicommerce gives us exactly one bot session, and its internal API is facility-scoped: switching facility is a stateful act on the session. Two parallel jobs would silently corrupt each other's facility context. Serial execution is a correctness guarantee, not a performance compromise. All UC calls are also throttled to 4 per second so we never trip their limits.
  4. The result lands back in the run row Success or failure, summary, counts, and any generated file (as base64) are stored on the run. The browser polls, renders it in plain words, and offers previews and downloads.

The two Unicommerce doors

Unicommerce has a public API (bearer token from the bot account's password, self-renewing, reliable) and an internal API (the one the browser UI uses, needing a JSESSIONID cookie captured after a human login). Most of what these automations need only exists on the internal API. The session is kept alive by a ping every 4 minutes; only HTTP 401, a redirect, or an explicit USER_NOT_LOGGED_IN body counts as session death. A 403 or a successful: false answer is a business response, never death.

why Early versions treated 403 as "session dead" and forced pointless re-logins. A wrong-facility query can 403 while the session is perfectly healthy. This distinction is enforced in one place (the UC client) so no automation can get it wrong.

2 · ASN Compile Unicommerce only

Input: one SO number. Output: that marketplace's ASN file, ready to upload to the marketplace portal.

  D -- yes --> E[Build rows

  1. Find the order, facility by facility POST /data/oms/saleorder/fetch with the SO code against each facility, Opp_RSG_MH first, until one returns the order. why An SO is only visible inside its home facility on the internal API; there is no global lookup. RSG goes first because most B2B orders live there, so the common case is one call, not five.
  2. Detect the marketplace from the order itself The order's own channel field (for example MYNTRA_B2B) picks the output format. Nobody chooses it manually. why The earlier manual picker let a Zepto order be compiled into a Flipkart-format file, which looks plausible and is completely wrong. Auto-detection makes that mistake impossible. Orders on channels with no ASN format (Amazon and others) get a clear refusal naming the channel.
  3. Turn line items into rows Items are aggregated by SKU, fully cancelled lines are dropped, and each row carries SKU, EAN, quantity, MRP, unit price excluding tax (derived from the selling price when Unicommerce omits it), HSN, tax split (CGST and SGST as half the rate each), invoice number, and PO.
  4. Write the marketplace's exact file Flipkart: two-header-row packaging XLSX. Myntra: ASN XLSX including its total-cost formulas. Zepto: seven-column CSV. All three layouts are byte-compatible ports of the proven Apps Script writers.
  5. Return it to the user The file goes back inside the run result as base64; the browser shows an inline preview and a real download link. why The legacy version saved files into a Drive folder, which meant hunting for them and sharing-permission problems. Handing the file straight back removes a whole class of "where did it go" confusion. The run row keeps it re-downloadable from history.

When it fails: "not found in any facility" means exactly that, because a dead session is detected separately and reported as a session problem, never disguised as a missing order.

3 · Reverse DC No external systems

Input: the original credit note PDF. Output: the same document turned into a Delivery Challan.

  1. Upload the credit note A direct file upload (15 MB cap, PDF only, validated by content not just filename). why The first version asked for a credit note number and tried to fetch the document. The correction from the field: users hold the PDF, so the PDF is the input.
  2. Edit the document in place Using a PDF library on the server: the barcode block is masked, the From and To parties are swapped (goods now flow back to Opptra), the title becomes Delivery Challan, and optional address lines the user typed replace the printed ones.
  3. Return it instantly This is the one automation that skips the queue and answers synchronously. why It touches no external system and takes under a second, so queueing would only add waiting. The queue exists to serialize Unicommerce access; no Unicommerce, no queue.

Where it stores, and why

Postgres · runswritemetadata only, not the PDFsUsage history without turning the database into a document archive; the documents belong to the user

4 · Packing Mail Unicommerce + Gmail

Input: a list of SO numbers. Output: one reviewed email per warehouse with the invoice PDFs attached.

flowchart LR
  A[SO list] --> B[Find each SO's
invoice + facility]

invoice PDF]
  C --> D[Group SOs
by warehouse]
  D --> E[One Gmail draft
per warehouse]

in Gmail}

  1. Resolve every SO's invoice For each SO, hop facilities calling fetchShippingPackageDetails until a package with an invoice number appears. SOs without one are reported back by name, not dropped.
  2. Download the invoice PDFs Each invoice comes down over the internal session via /oms/invoice/show, the same proven route the legacy tools used.
  3. Group by warehouse and draft The facility-to-email mapping decides recipients. One draft per warehouse: greeting, order list, invoices attached, sent from the connected Opptra account.
  4. Draft first, always; then one-click send The result screen shows each draft with a "view in Gmail" deep link and a "send now" button. Send dispatches the exact draft that was reviewed, via Gmail's draft-send call. why These emails go to external warehouse partners. A blind auto-send that grouped the wrong orders would be a real-world incident. The draft is the safety gate, and sending the reviewed draft (rather than composing again at send time) means what was checked is exactly what goes out.

5 · Sheet Update Neon + Sheets + Unicommerce

Keeps the team's B2B tracking sheet current without anyone copying rows by hand. Four actions share one data model.

The data model first

Two spreadsheets exist. The ops team's original ("B2B-VIEW-INDIA") is read-only to us, always. Our working copy is where automation writes: a Master tab holding everything, plus one dated tab per day (like 24-Jul-2026) holding only that day's new orders. Row 1 is a colour banner, row 2 holds the column headers, data starts at row 3. Columns are always found by header name, never by position.

why The ops team owns that sheet's layout and reorders columns when they need to. Position-based writing breaks the day someone drags a column; name-based writing survives it. And the original stays read-only so no automation bug can ever damage the ops team's source of truth. 
flowchart LR
  N[(Neon DB
Waypoint's data)] -- first fill --> T[Today's tab]
  T -- auto push --> M[Master tab]
  U[(Unicommerce)] -- second fill:
invoice, tracking, status --> M

First fill · new orders in

  1. Read today's orders straight from Waypoint's database A read-only SQL query joins orders, line items (brands, units) and appointments in Neon, already filtered to CREATED and not suppressed. why The old path scraped Waypoint's CSV export with a login cookie that kept expiring. The database is the same truth with no session to babysit, structured joins instead of CSV parsing, and it can never silently serve yesterday's file.
  2. Translate to the sheet's vocabulary Marketplace codes become the sheet's dropdown labels (AMAZON_B2B → "AZ Etrade", ZEPTO_B2B → "Zepto"), statuses become ops language (CREATED → "Pickup Pending"), dates become clean date strings. why The Master's columns are dropdown-validated. Writing raw system codes would break the ops team's filters and make the sheet reject edits.
  3. Write only what's genuinely new, then push to Master in the same run Anything already on Master is skipped; the rest lands on today's tab and is immediately appended to Master too. Both writes dedupe by SO number, so re-running is always safe.

Where new rows land: the hard-earned rule

New rows are written at the row right after the last row that has an SO number. This exact rule exists because both obvious alternatives corrupted the real sheet: Google's own append API treated the empty banner cell as an empty table and overwrote the headers and the oldest rows, and the legacy "first empty cell" scan landed in a mid-data gap and overwrote live rows. Below the data also sit about 25,000 invisible leftover formula cells that make "last non-empty row" lie. The last-SO-row rule can only ever overwrite rows that hold no orders. It is enforced by regression tests, and the append API is banned from the codebase outright.

Second fill · enrichment from Unicommerce

  1. Collect rows still missing an invoice Today's tab plus Master are scanned for rows with a blank invoice column (capped per run to stay within quotas).
  2. Ask Unicommerce about each one Packages give invoice number, tracking, transporter, dispatch type, e-way bill and quantity (trying the row's own warehouse first); the order summary gives overall status and destination; a final invoice-details lookup catches invoices the packages missed, skipping credit notes.
  3. Patch cells by header name, in one batch Only non-empty values are written, only into rows matched by SO number, all in a single batched Sheets call. why Patch-only means the automation can never blank out something ops typed by hand. One batched call instead of hundreds keeps us far from Google's per-minute write quota.

Hourly source sync · drift protection

  1. Compare the read-only source against our Master Every hour (and on a button), any order present in the ops source sheet but absent from our Master is copied over, header-mapped across the two different layouts.
  2. Add missing only, never update existing Rows already on our Master are never touched by the sync. why Our Master's rows carry enrichments (invoices, tracking) that the source doesn't have. A sync that "updated" existing rows would erase our own work. Add-missing-only makes the sync idempotent: the button and the hourly cron can even overlap harmlessly.

6 · Everything the platform stores, and why

The platform deliberately stores coordination data, not business data. Orders live in Unicommerce, rows live in the Sheet, mail lives in Gmail. What the server keeps is the minimum needed to be reliable and auditable:

StoreHoldsWhy it exists
usersemail, role, active flagGoogle proves identity; this table decides authority. Deactivation is instant because every request re-checks it.
runsevery automation run: who, what, when, resultThe audit trail, the dashboard, re-downloadable files, and honest failure reporting. Users see only their own; admins see all, enforced server-side.
audit_logappend-only security eventsLogins, role changes, session updates. Append-only so history can't be rewritten.
uc_sessionone row: the Unicommerce cookie + livenessExactly one bot session exists, so exactly one row (the schema enforces id = 1). Liveness fields drive the status pill everyone sees.
google_oauth_tokenone row: the Gmail/Sheets refresh tokenGranted once by an admin through Google's own consent screen. Server-side only; the browser never sees it. Chosen over a service account because org policy blocks key export, and this path needs no IT approvals.
step_ledgermemo of completed side-effect stepsIdempotency: a retried job replays its finished steps from the ledger instead of re-creating a PO or invoice twice.
ingest_tokenshashed helper-extension tokensLets the session-capture extension post a fresh cookie. Stored hashed, so a database leak leaks nothing usable.
Redisthe job queue and the two schedulersQueue survival across restarts, plus the 4-minute session ping and the hourly sheet sync. No business data lives here.
Server disknightly database backups, 14-day rotation2:30 AM IST, automatic. The sheet has Google version history; Unicommerce is its own system of record.
