Unicommerce Supply-Chain Automation

One backend, one web app, every automation.

A single Node.js platform that runs all of Opptra's supply-chain automations on top of Unicommerce. Humans sign in with Google; the backend owns one Unicommerce session and does the work. Every action is queued, attributed, and audited.

Node 20 · TypeScript-ready Fastify · BullMQ · Postgres · Redis Google Cloud · Docker Compose One static IP for UC whitelisting

01 System architecture

Five containers on one box. The API only accepts requests and enqueues work; the worker is the only process that talks to Unicommerce, so exactly one process owns the session.

Attribution on a shared account. Everyone shares one Unicommerce bot login, but every click creates a runs row — who, what, which SO, result. The Dashboard answers “who ran what” without anyone guessing.
Role checks re-read the database on every request, so deactivating or demoting a user takes effect immediately, not when their 12-hour token expires.

03 Unicommerce session lifecycle

Internal /data calls need a browser JSESSIONID that idles out in minutes. One owner keeps it alive; when it dies, an admin re-logs in and the worker adopts the new cookie within a second.

%%{init:{'theme':'base','themeVariables':{'fontFamily':'ui-sans-serif, system-ui','primaryColor':'#eef1f8','primaryBorderColor':'#131A48','primaryTextColor':'#131A48','lineColor':'#FF5800'}}}%%
sequenceDiagram
  autonumber
  participant Ad as Admin
  participant API
  participant DB as uc_session (Postgres)
  participant WK as Worker (session owner)
  participant UC as Unicommerce
  Note over WK,UC: keep-alive every ~4 min
  WK->>UC: ping facilities endpoint
  UC-->>WK: 200 → mark ALIVE
  Note over WK,UC: cookie idles out → 401
  WK->>DB: mark DEAD + alert
  Ad->>API: paste fresh JSESSIONID
  API->>DB: store cookie + enqueue keepalive
  WK->>DB: reload cookie (adopt paste)
  WK->>UC: ping with new cookie
  UC-->>WK: 200 → ALIVE (within ~1s)
Session death is narrowly defined: only 401, a login redirect, or USER_NOT_LOGGED_IN. A 403 or successful:false is a business response, never “dead” — a hard-won lesson kept as a test.
Temporary by design. Paste is the bridge until Unicommerce whitelists our account; then the backend scripts login itself and the paste step disappears. The static IP is what makes the whitelist hold.

04 Request lifecycle

Every automation follows the same path, so a new one is a known quantity: validate → record → enqueue → run → report.

%%{init:{'theme':'base','themeVariables':{'fontFamily':'ui-sans-serif, system-ui','primaryColor':'#eef1f8','primaryBorderColor':'#131A48','primaryTextColor':'#131A48','lineColor':'#FF5800'}}}%%
sequenceDiagram
  autonumber
  participant UI as Web SPA
  participant API
  participant Q as Redis
  participant WK as Worker
  participant EX as UC / Google
  UI->>API: POST /api/automations/…  (JWT)
  API->>API: auth → validate → rate-limit
  API->>API: create run (queued)
  API->>Q: enqueue { runUid, input }
  API-->>UI: { runUid }
  WK->>Q: pick up job
  WK->>EX: run pipeline (paced, idempotent)
  WK->>API: finishRun (succeeded / failed)
  UI->>API: poll /api/runs/{runUid}
  API-->>UI: result → render card
One contract everywhere: jobs are always { runUid, input }. That shape is unit-tested against the worker, so a mismatch can’t reach production (it once did — now it can’t).

07 Reliability by design

The properties that keep it steady in production, not just working in a demo.

Global rate limiting

One token bucket paces every Unicommerce call across all automations; HTTP 429 is honored with back-off. It can't trip the throttle.

Durable idempotency

Multi-step flows memoize each step per request in Postgres — a retry resumes and never double-creates a PO, invoice, or allocation.

Single session owner

Only the worker (concurrency 1) touches Unicommerce, so facility context and the cookie are never raced.

Fail loud

Dead session, stuck job, or generation failure raises a deduped alert; the Dashboard shows session and run health.

Full attribution

Every action is a run row; security events are an append-only audit log.

Tested

Unit tests cover session semantics, rate limiting, idempotency, and each pipeline — green on every change.
