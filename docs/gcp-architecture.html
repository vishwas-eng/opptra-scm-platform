Opptra SCM Platform

One VM. One static IP. Nothing else on Google Cloud.

The whole backend, API, worker, database, queue, TLS, runs as five containers on a single Compute Engine instance. Google Cloud's job is narrow: hold that box, and give it one fixed address Unicommerce can whitelist.

₹2,500–3,500/ month, all-in

Infrastructure

Three nested boundaries: the public internet, the Google Cloud project, and the VM's private Docker network. Only Caddy is reachable from outside, Postgres and Redis never leave the box.

Static IP

The one resource everything hinges on, the address Unicommerce whitelists.

Public-facing container

Caddy, API, worker, reachable inside the VM's network, only Caddy from outside.

Internal-only store

Postgres, Redis, no published port, never touch the internet.

Outside the project

Users, Unicommerce, Google Workspace, everything the platform talks to.

Google Cloud resources

The entire GCP footprint. One API enabled, one machine, one address, one firewall rule.

ResourceSpecWhy
API enabledcompute.googleapis.comThe only Google API this project uses.
VMe2-medium · 2 vCPU · 4 GB RAM · Debian 12 · 50 GB balanced diskRuns all five containers; no GPU, no managed DB needed at this scale.
Static IP1 reserved external addressWhat gets sent to Unicommerce for whitelisting, must never change.
Firewall ruleAllow tcp:80, tcp:443 onlyEverything else stays closed; SSH via IAP/allowlist, not a public port.
Regionasia-south1 (Mumbai)Lowest latency to Unicommerce and NIC; data stays in India.

What runs on the box

Five containers, brought up with one docker compose up.

ContainerImageRole

Why this shape

Each thing this design leaves out was a real option, considered and set aside for a specific reason.

Why not Cloud SQL / Memorystore for Postgres and Redis?
At ~10 users and a handful of automations, self-hosted Postgres and Redis on the same box are simpler and cheaper. Backups are a nightly pg_dump cron rather than a managed line item.
Why not Cloud Run?
Cloud Run needs a VPC connector plus Cloud NAT just to get a static outbound IP, and a static IP is mandatory for the Unicommerce whitelist regardless. That's extra cost and moving parts for no benefit over one VM.
Why not a load balancer or Kubernetes?
Exactly one worker process is allowed to own the Unicommerce session at a time, that's a correctness rule, not a scaling limit. There's nothing to horizontally scale yet.
What changes if this outgrows the box?
Bump the machine type. The static IP, the containers, and the architecture stay identical, no rebuild.
